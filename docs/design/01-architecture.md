# Tessync 구조 설계 (v0)

아이폰 화면을 핫스팟으로 연결한 테슬라 내장 브라우저에 미러링하는 iOS 앱. 최우선 목표는 **장시간 끊기지 않는 것**이다.

## 1. 전체 구조

```
iPhone                                                      Tesla
┌──────────────────────────────────────────────┐           ┌─────────────────────────┐
│ 메인 앱 (SwiftUI)                             │           │ 내장 브라우저           │
│  - 방송 시작 버튼 (RPSystemBroadcastPicker)   │           │                         │
│  - 접속 주소 표시, 설정, 진단 로그 보기       │           │  http://172.20.10.1:8080│
│                                              │           │   ├ index.html          │
│ Broadcast Upload Extension (실제 엔진)        │  Wi-Fi    │   ├ player.js           │
│  ReplayKit 프레임                            │ (개인용   │   └ WebSocket /stream   │
│   → 다운스케일 (VTPixelTransferSession)       │  핫스팟)  │        ↓                │
│   → 하드웨어 인코딩 (VTCompressionSession)    │ ───────▶  │  디코드 → <canvas>      │
│   → WebSocket 전송 (Network.framework)        │           │                         │
│  HTTP 서버: 플레이어 페이지 제공               │           │                         │
│                                              │           │                         │
│ App Group 공유 컨테이너: 설정, 진단 로그       │           │                         │
└──────────────────────────────────────────────┘           └─────────────────────────┘
```

- 메인 앱은 백그라운드로 가면 중단되므로 **캡처, 인코딩, 서버 전부를 Broadcast Upload Extension 안에서** 돌린다.
- 트래픽은 폰과 차 사이에서만 오가므로 데이터가 소모되지 않는다.
- 오디오는 v1에서 미러링하지 않는다. 테슬라는 이미 블루투스로 폰과 연결되어 있으니 소리는 블루투스로 나온다(FluxCast/TslaMirror의 MJPEG 모드와 같음).
- 터치 제어는 불가능하다(iOS에 터치 주입 API가 없음). 보기 전용.

## 2. 끊김 원인과 대책

미러링 앱이 끊기는 원인은 대부분 아래 중 하나다. 각각을 설계 단계에서 막는다.

### 2-1. 익스텐션 메모리 초과로 강제 종료 (가장 유력한 원인)

Broadcast Upload Extension은 메모리 한도가 약 50MB다. 넘으면 시스템이 경고 없이 죽인다. 네트워크가 잠깐 느려질 때 프레임이 큐에 쌓이면 바로 한도를 넘는다.

대책:
- **큐 길이를 고정한다.** 인코딩 전 대기 프레임 최대 1개, 전송 대기 최대 2~3개. 넘치면 새 프레임을 버린다(오래 쌓아두지 않는다).
- **전송이 밀리면 인코딩 자체를 건너뛴다.** 소켓의 미전송 바이트가 임계값을 넘으면 다음 프레임을 인코딩하지 않는다. 회복되면 키프레임을 요청해서 이어 붙인다.
- **픽셀 버퍼는 풀(CVPixelBufferPool)에서 재사용**하고, CIImage/CGImage 변환이나 복사를 하지 않는다.
- **해상도를 먼저 줄인다.** 아이폰 원본(약 1179x2556)을 그대로 인코딩하지 않고 최대 1280px 안쪽으로 다운스케일한 뒤 인코딩.
- **메모리 사용량을 1초마다 기록한다**(`task_vm_info.phys_footprint`). 40MB를 넘으면 해상도/품질을 자동으로 낮춘다.

### 2-2. 화면 잠금으로 방송 종료

iOS는 화면이 잠기면 방송을 강제로 끝낸다. 앱이 막을 수 없고, 방송 재시작도 사용자가 직접 눌러야 한다.

대책:
- 첫 실행 안내에서 **자동 잠금을 "안 함"으로** 바꾸도록 안내한다(설정 > 디스플레이 및 밝기).
- 방송이 끊기면 차 화면에 "폰에서 다시 시작을 눌러주세요" 안내를 띄운다(브라우저 쪽에서 감지).
- 메인 앱에 방송 시작 위젯/단축어를 두어 재시작을 한 번의 탭으로 만든다.

### 2-3. 핫스팟/Wi-Fi 연결 끊김

- **테슬라가 다른 Wi-Fi로 갈아타는 문제**: 집이나 회사 Wi-Fi가 저장되어 있으면 근처에서 그쪽으로 붙을 수 있다. 안내 문서에 포함.
- **핫스팟에 인터넷이 없으면** 테슬라가 Wi-Fi를 버리고 LTE로 갈 수 있다. 셀룰러 데이터는 켜둔 상태로 둔다.
- **90초 무통신 자동 해제**: Apple 문서상 핫스팟은 90초 동안 트래픽이 없는 기기를 끊는다. 화면 변화가 없어도 1초 하트비트가 계속 흐르므로 이 문제를 피한다.
- **핫스팟 주소**: iOS 18 이상 + IPv6 통신사에서는 IPv6를 쓰는 기기가 192.0.0.2(게이트웨이 192.0.0.1)를 받고, 이 주소로는 아이폰 서버에 접속되지 않았다(맥에서 확인). IPv4 전용 기기는 172.20.10.x를 받는다. 테슬라가 어느 쪽인지 실차 확인 필요.
- **5GHz 사용**: "호환성 최대화"를 끄면 5GHz로 열린다. 대역폭과 간섭 면에서 유리하다(Tesor도 5GHz를 요구).
- **저전력 모드 끄기**: 저전력 모드에서는 네트워크와 인코더가 제한된다(TslaMirror도 요구).
- TesMirror는 "D 기어 진입 후 핫스팟 재연결 필요"를 언급한다. 실차에서 재현되는지 0단계에서 확인한다.

### 2-4. 브라우저 쪽 문제

- **탭이 멈추거나 소켓이 끊김**: 테슬라에서 다른 화면(공조, 카메라 등)을 열었다 돌아오면 소켓이 끊길 수 있다.
  → 플레이어는 **하트비트**(서버가 1초마다 ping)로 연결을 감시하고, 3초 동안 응답이 없으면 즉시 재연결한다. 재연결은 0.5초 → 1초 간격으로 계속 시도.
- **재연결 직후 화면이 깨짐**: H.264는 키프레임부터 디코딩해야 한다.
  → 새 접속이 들어오면 서버가 **즉시 키프레임을 강제 생성**한다. 평소에도 키프레임 간격을 2초로 짧게 둔다.
- **화면 변화가 없을 때 끊긴 것으로 오해**: ReplayKit은 화면이 바뀔 때만 프레임을 준다. 그래서 영상 프레임이 아닌 하트비트로 생존을 판단한다.
- **브라우저 메모리 누수**: MSE(`<video>`)는 버퍼가 쌓이면 브라우저가 죽을 수 있다. canvas에 직접 그리는 방식을 기본으로 하고, 매 프레임 비트맵을 즉시 해제(`ImageBitmap.close()`, `VideoFrame.close()`)한다.
- **디코더 오류**: 오류가 나면 디코더를 재생성하고 키프레임을 요청한다. 그래도 반복되면 페이지를 새로고침한다.

### 2-5. 발열로 인한 성능 저하

- 장시간 사용하면 아이폰이 뜨거워져 인코더가 느려진다.
- `ProcessInfo.thermalState`에 따라 fps(30 → 20 → 15)와 비트레이트를 단계적으로 낮춘다.

### 2-6. 끊김 원인을 알 수 있게 진단 로그

FluxCast가 왜 끊기는지 사용자는 알 수 없었다. 우리는 원인을 기록한다.
- 익스텐션이 App Group 컨테이너에 기록: 메모리, fps, 비트레이트, 전송 지연, 접속/해제 시각과 사유, 발열 상태
- 방송 종료 사유(`broadcastFinished`, 화면 잠금, 오류 코드)
- 메인 앱에서 로그를 보고 공유할 수 있게 한다.

## 3. 영상 방식

| 방식 | 장점 | 단점 | 대상 |
|---|---|---|---|
| **MJPEG over WebSocket → canvas** | 가장 단순하고 안정적. 프레임마다 독립이라 하나 빠져도 문제없음. 보안 컨텍스트 불필요 | 대역폭 큼 (720p 30fps 기준 대략 15~25Mbps) | v1 기본값, MCU2 |
| **H.264 → WebCodecs → canvas** | 대역폭 작음, 화질 좋음 | WebCodecs는 **HTTPS(보안 컨텍스트)에서만** 동작 | v2 |
| H.264 → MSE `<video>` (jmuxer 방식) | HTTP에서도 동작 | 버퍼 지연, 메모리 누적. 주행 중 `<video>` 재생이 막힌다는 보고가 있어 확인 필요 | 대체 경로 |
| H.265 | 대역폭 최소 (FluxCast가 MCU3에서 사용) | 브라우저 지원 확인 필요 | v2 |

**v1은 MJPEG로 시작한다.** 끊김 없는 안정성이 최우선이고, 프레임 하나가 빠져도 다음 프레임이 독립적으로 그려지므로 복구가 필요 없다. JPEG 인코딩도 VTCompressionSession(하드웨어 JPEG)으로 처리한다.

**H.264/H.265(v2)는 HTTPS가 필요하다.** 로컬 IP는 공인 인증서를 받을 수 없으므로 다음 방식을 검토한다.
- 사용자별 서브도메인(예: `<기기ID>.local.tessync.app`)이 `172.20.10.1`을 가리키게 하고, 서버에서 DNS-01로 인증서를 발급받아 앱에 내려준다(Plex의 `plex.direct` 방식).
- 공용 인증서와 개인키를 앱에 넣는 방식은 인증서가 폐기될 수 있어서 쓰지 않는다.

## 4. 개발 단계

### 0단계: 테슬라 브라우저 실측 (가장 먼저)

추측으로 설계하지 않도록 차에서 먼저 측정한다. 진단 페이지를 하나 만들어 테슬라 브라우저에서 연다.
- User-Agent, Chromium 버전, 화면 해상도, devicePixelRatio
- `isSecureContext`, `VideoDecoder` 지원 여부와 코덱별 지원(avc1, hvc1)
- MSE 코덱 지원(`MediaSource.isTypeSupported`)
- `createImageBitmap`, WebGL 지원
- **주행 중** `<video>`와 canvas 각각이 계속 그려지는지
- 핫스팟 IP와 D 기어 전환 시 Wi-Fi 유지 여부

### 1단계: MVP

- 메인 앱 + Broadcast Upload Extension
- MJPEG, 720p, 30fps
- HTTP 서버와 WebSocket(Network.framework, 외부 라이브러리 없음)
- 플레이어: 하트비트, 자동 재연결, canvas 렌더링, 가로 화면 맞춤
- 진단 로그

### 2단계: 장시간 안정성 테스트

- 2시간 연속 미러링 목표. 끊김 횟수, 메모리 최고치, 발열을 기록한다.
- 일부러 상황을 만들어 테스트: Wi-Fi 끊었다 붙이기, 테슬라 다른 화면 왕복, 유튜브 재생으로 화면 변화 최대화.

### 3단계: 화질 개선

- HTTPS 인증서 체계, H.264/H.265 + WebCodecs
- 네트워크 상태에 따른 비트레이트 자동 조절

### 이후

- 오디오 미러링(WebAudio). 블루투스로 충분한지 사용자 반응을 보고 결정.

## 5. 그 밖의 고려 사항

- **DRM 앱**: 넷플릭스 등은 검은 화면이다. 모든 미러링 앱에 공통이다.
- **법규**: 도로교통법 제49조는 운전 중 영상 표시를 금지한다(지리안내/교통정보 영상은 예외). 앱 안내에 주의 문구를 넣고, 영상 시청 용도로 홍보하지 않는다.
- **앱스토어 심사**: TslaMirror, FluxCast 등이 이미 통과했으므로 같은 범주로 심사받는다. 운전 중 사용 경고 문구를 포함한다.
- **개발 환경**: 실제 아이폰과 맥(Xcode)이 필요하다. ReplayKit은 시뮬레이터에서 테스트할 수 없다.
